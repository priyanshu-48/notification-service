# Load test results

Measured 2026-10-07/08 with `loadtest/run-local.sh` and `loadtest/notifications.js`. The Docker image was rebuilt from the repository (source identical to commit `2198e13`) before the runs; its id is in `docs/evidence/loadtest/idle-baseline.txt`. Machine and versions: `docs/evidence/ENVIRONMENT.md`. Raw output for every run: `docs/evidence/loadtest/raw/` (plus `raw-no-sampler/`); tables generated by `scripts/evidence/summarize-load.py` are in `docs/evidence/loadtest/summary.md`.

## Method
- Production image, API and worker in one process (`RUN_WORKER=true`, worker concurrency 10), mock email channel, fresh throwaway Postgres database per run, Postgres on the same laptop.
- k6 (Docker image `grafana/k6`, v2.3.0) sends `POST /v1/notifications` at a constant arrival rate for 60 s (50 seeded users, channels `email` and `in_app`, a unique `Idempotency-Key` each), then waits until nothing is in flight. 15 s pause between runs.
- "Accepted" is k6's count of 201 responses. "Delivered" is counted from Postgres after the run (`notifications` rows in `delivered`), not from k6. Every run: delivered = accepted, failed = 0, nothing left queued or sending.
- "e2e per minute" = notifications completed divided by the whole run including user seeding and the drain wait, so it understates peak throughput at low rates and is the right figure for sustained throughput at overload.
- Capped runs: `--cpus=0.1 --memory=512m`; Redis either a separate uncapped container or embedded in the capped container (`EMBEDDED_REDIS=1`, as deployed on Render).
- A sampler recorded `docker stats` for the app and k6 containers roughly every 2 s (`*.txt.stats`). Because the sampler itself uses CPU, the uncapped 100/200/300 rates were repeated 3 more times without it (`raw-no-sampler/`).

Ceiling search (uncapped, **single run each**): 400/s accepted 23,934 of 24,000 (66 dropped by k6), p95 140 ms; 500/s 29,786 of 30,000, p95 440 ms; 600/s 32,145 of 36,000, p95 1.01 s; 800/s 31,982 of 48,000, p95 1.03 s. All accepted notifications were delivered. First dropped requests: 400/s. p95 passes the script's 500 ms threshold between 500/s and 600/s. The API's acceptance plateaus near 32,000/min.

Sustained delivery: completed per minute across the whole run was 11,154 / 10,857 / 10,718 / 10,526 at 400 / 500 / 600 / 800/s, and 11,332-11,999 at 300/s. So the worker drains about 175-190 notifications per second (each to two channels) on this machine. Above about 200/s the queue grows; at 300/s it took about 30-48 s after the 60 s of sending to empty.

Capped capacity under overload (e2e per minute at 40/s): embedded **943** (918-951), separate **1,010** (967-1,017). Embedded Redis therefore costs about **7%** (about 2-10% from the extremes) at saturation. At 20/s (still under capacity) the figures were 818 vs 860, about 5%.

## Load generator cost
`docker stats` samples (max of the run, percent of one core): k6 about 12% at 100/s, 25% at 200/s, 34% at 300/s, 43-64% at 400-800/s; the app container 78-128% (about 1.3 cores) uncapped. k6 and the app ran on different cores of a 20-thread machine, so k6 did not take CPU from the app directly, but both share caches, memory bandwidth and Docker Desktop's VM.

## Things not to over-read
1. Latency varied run to run: 300/s p95 was 45.6-55.3 ms in the first three runs and 67.5-81.3 ms in the later three without the sampler. An earlier single run reported 24 ms; **it was not reproduced**. Quote a range, not 24 ms.
2. **18,000/min is the accepted rate, not the delivered rate.** Sustained delivery is about 10,500-11,500/min on this machine.
3. All ceiling figures are single runs.
4. Mock email channel (instant), Postgres on the same machine, no network between k6 and the API beyond Docker's. A real provider would bound throughput instead.
5. A laptop under Docker Desktop is not Render. These numbers are not predictions for the deployed service.
6. During the runs, two unrelated containers (`ai-course-backend`, `ai-course-redis`) were running but idle (about 1% CPU in the baseline).
